# 摄像机字段

> 全部语义由用户用 Cheat Engine **逐项改写后目视判定**，不是推测
> 原始记录：reports/20261009_150703_原版_CCamera_字段语义用户判定.txt

## 指针链

    cam = *( *(hoi4.exe + 0x332F698) + 0x750 )

getter 是 sub_140DC53B0（RVA 0x0DC53B0）：

    return *(_QWORD *)(a1 + 1872);      // 1872 = 0x750

## 写入方式：直接写字段，不要用 setter（2026-10-10 定论）

**曾经的做法**：调 `sub_1412643F0(cam, h)`（RVA 0x12643F0）当作 setter。
该函数被 37 处引用，反编译看净效果确实是 `cam+0x69C = h`。

**但它是不可靠的** —— 实测中调它之后 `+0x69C`、`+0x684`、`+0x678` 全都变成了目标值，
**画面却纹丝不动**（改 `+0x678` 也没用）。

**决定性实验**（CE MCP 桥接，直接写内存后定时读回）：

    基线      A.y=966.44   B.y=966.42   D.y=966.30   in1.y=966.42
    直接写 +0x69C = 2000
    +0.5s     A.y=1999.84  B.y=1999.86  D.y=2000.00  in1.y=1999.86
    +6.5s     A.y=1999.84  B.y=1999.86  D.y=2000.00  in1.y=1999.86

**直接写 `+0x69C` 完全有效**：0.5 秒内 A/B/矩阵输入全部跟随，且稳定不回退。

**⇒ 结论：`Camera_SetHeight` 只做一件事 —— 直接写 `+0x69C`（float）。不调任何游戏函数。**

### 相关函数（仅供理解，我们不再调用前四个写入口）

| 函数 | 语义 |
|---|---|
| `sub_140DC53B0(idler)` | 取 cam（CInGameIdler 虚表 `+0x130`） |
| `sub_141264150(cam)` | 滚轮向下（高度减小） |
| `sub_1412642A0(cam)` | 滚轮向上（高度增大） |
| `sub_1412643F0(cam, h)` | 名义上的"设置高度"，**实际不可靠，已弃用** |
| `sub_141261320(cam, ...)` | 内部插值（上面三个都调它） |

`sub_141261320` 里会把 `+0x684` 夹到 `[+0x6D0, +0x6D4]`。

详见《找 setter 的方法》与 `test/reports/20261009_173105_*.txt`。
## 字段语义（已定论）

| 偏移 | 类型 | 含义 |
|---|---|---|
| **+0x69C** | float | **目标高度（引擎承认的设置入口）** |
| +0x678 | float | 当前高度（游戏自己平滑逼近 +0x69C） |
| +0x684 | float | 渲染层副本（改了会被拉回，非引擎层） |
| +0x6D0 | int | **高度下限** |
| +0x6D4 | int | **高度上限** |
| +0x6F4 | float | 鼠标拖动阻尼（调大后漂移感消失） |
| +0x6F0 | byte | 摄像机锁定标志 |
| +0x674 | float | 位置 X |
| +0x678 | float | 位置 Y（同时就是高度） |
| +0x67C | float | 位置 Z |
| +0x6C8 | int | 视口宽 |
| +0x6CC | int | 视口高 |
| +0x690 | float | 常量 9.5，改写后立即回写 |
| +0x6F8 | int | 疑似 1，改动无明显效果 |
| +0x6FC | float | **语义未定**（与高度负相关） |

## 上下限可写（2026-10-09 实证）

`+0x6D0` / `+0x6D4` 是 **int**（不是 float）。用 Frida 读原始字节确认：

    +0x69c  u32=1134231552  i32=1134231552  f32=310.0000   <- 高度 (float)
    +0x6d0  u32=50          i32=50          f32=0.0000     <- 下限 (int)
    +0x6d4  u32=3000        i32=3000        f32=0.0000     <- 上限 (int)

**直接写这两个字段即生效**，不需要额外的 setter —— setter 的夹紧逻辑读的就是它们。

实测（把上下限改成 `[100, 2000]` 之后）：

| 操作 | 结果 |
|---|---|
| `setcamheight 5000` | 高度 = **2000.00**（被新上限夹住） |
| `setcamheight 10` | 高度 = **100.00**（被新下限夹住） |

## 上下限的四条约束（用户要求，已实现）

| 约束 | 做法 |
|---|---|
| **真-下限 = 35** | 硬编码 `CAM_TRUE_LOWER 35`；设下限小于 35 时夹到 35（**用 1 会把视角拉进地里**） |
| **真-上限 = 游戏初始值** | 运行期首次拿到 cam 时捕获当时的上限（3000）作为真-上限；超过则夹到它 |
| **高度必须落在范围内** | 改完上下限后**平滑地**把高度推到边界（见下一节）|
| **上下限必须有序** | 设下限后若 下限>上限 则 上限=下限；设上限后若 上限<下限 则 下限=上限 |
| **上下限跨度不小于 50** | `CAM_MIN_SPAN 50`；跨度不足时抬上限（否则游戏归一化 `(h-lo)/(hi-lo)` 会除零出 NaN）|

超界夹紧：

    [setcamupper] clamp 9000 -> true upper 3000
    [setcamlower] clamp 0 -> true lower 35

## 平滑过渡：下限与高度必须【同步推进】（2026-10-10 定论）

**机制（CE 追踪实证）**：

    start  D=2600.0  A=2599.9
    01     D=2561.1  A=2599.9      <- D 在降, A 还没动
    02     D=2522.2  A=2594.6      <- A 开始跟
    ...
    08     D=2288.9  A=2500.0      <- A 停在下限 (当时下限=2500)
    09~18  D=2250→1900  A=2500.0   <- A 死活不下来
    END    D=2500.0  A=2500.0      <- 连 D 都被弹回下限

由此确定三件事：

1. **A（`+0x678`）跟随 D（`+0x69C`）**，由游戏每帧插值，速率很快（0.5 秒内到位）
2. **下限（`+0x6D0`）是硬限制**：游戏每帧把低于下限的 A 钳上去，**连 D 也会被弹回**
3. 所以要"平滑地抬高度"，**必须同时平滑抬下限**，否则两者互相打架

**三次尝试的对照**：

| 版本 | 做法 | 结果 |
|---|---|---|
| 1 | 平滑写高度，下限一次性设 2500 | **瞬间跳**（下限把高度钳走） |
| 2 | 只平滑抬下限，不动高度 | **完全不动**（A 跟的是 D，不是下限） |
| 3 | **高度 + 下限同步平滑** | **成功，平滑上升** |

**实现**（`camera_height.c`）：一个统一的平滑线程，参数 `CAM_SMOOTH_STEPS 18`、
`CAM_SMOOTH_STEP_MS 16`（约 0.29 秒，匀速线性）：

    kind=1 平滑高度(+0x69C)
    kind=2 平滑下限(+0x6D0)
    kind=3 平滑上限(+0x6D4)
    withHeight=1 时，每一步【先推进高度, 再推进下限】

入口：`Camera_SetLowerLimitSmooth` / `Camera_SetUpperLimitSmooth`
（上限方向相反：上限降低时把高度往下推）。

后台线程执行，**不能在指令里同步等待** —— 那会卡住游戏主线程，画面反而不刷帧，看不到平滑。
忙时（上一次平滑未完成）退化为立即写入，避免线程堆积。

实测日志：

    [smooth] kind=2 from=50.00 to=2500.00 step=136.11 withHeight=1
    [smooth] done kind=2 final=2500.00 (readback 2500.00) height=2500.00
                (下限 50->2500, 18 步, 299ms)
    CE 抓到中间态: A.y=2363.00  <- 证明确实在平滑

### tooltip 显示夹紧后的值（已修）

tooltip 走 `sub_140544C90(self+0x58, &fixed, ctx, 0, 0)` 取参数，其快速路径是：

    if ( *(_BYTE *)(a1 + 9) )            // a1 = self+0x58，即 self+0x61 标志
        *a2 = *(_QWORD *)(a1 + 64);      // 即 self+0x98 的 8 字节定点值

dump 吻合：`self+0x60 = 0x00000101`（`+0x61` 标志已置位）、`self+0x98 = 0x08F0D180`（1500×100000）。

所以夹紧后**回写 `self+0x98`（定点）** 即可让文本与实际值一致：

    Effect_SetParamFixed(self, (double)finalValue);

修复前后：

    修复前: text=[设置摄像机高度上限：9000.00。]   <- 脚本原始值
    修复后: text=[设置摄像机高度上限：3000.00。]   <- 实际生效值

    setcamheight 800              ->  Camera Height is 800, moving from 310 (range [50,4000])

## 三个视图与视图矩阵（2026-10-10 静态分析 + CE 实证）

摄像机对象内有 **3 个独立视图**，各有自己的 4x4 矩阵与矩阵输入坐标：

| 视图 | 矩阵位置 | 矩阵输入 (x / **y=高度** / z) |
|---|---|---|
| V1 | `cam+16` | `cam+0x190` / **`+0x194`** / `+0x198` |
| V2 | `cam+560` | `cam+0x3B0` / **`+0x3B4`** / `+0x3B8` |
| V3 | `cam+1104` | `cam+0x5D0` / **`+0x5D4`** / `+0x5D8` |

每帧更新函数 `sub_141261960` 的核心模式：

    *(QWORD*)(a1 + 400) = *(QWORD*)(a1 + 1664);   // cam+0x190 <- cam+0x680 (B 组)
    sub_1422D9380(a1 + 16, ...);                  // 重算 V1 矩阵
    ...  V2、V3 同样处理

`sub_1422D9380` 是矩阵构建函数（读 `a1+384/396/408` 三个输入，输出 4x4 = 128 字节）。
构造函数 `sub_141260FB0` 里有一份同样逻辑（3 次调用 `sub_1422D9380`），
并用 `sub_1422D8300` 三次初始化三个矩阵。

**CE 实测：`in1.y` 恒等于 `B.y`**，与反编译的 `*(a1+400) = *(a1+1664)` 完全吻合。

**用户目视判定**：

| 操作 | 结果 |
|---|---|
| 改三个视图的 `in.y` | 影响**天空盒** |
| 锁 V1 B 组 = 2500 | 画面一直尝试往 2500 拉，但拉不到 |
| 锁 V1 D 组 = 2500 | 被锁在 2500 **附近**（仍能小幅拉动），说明 D 之上还有更权威的东西 |

**注意**：三个视图的 `in.*` **不是**实际视角高度，改它们只影响天空盒。
实际高度仍是 A（`+0x678`，跟随）/ D（`+0x69C`，目标）那一组。
