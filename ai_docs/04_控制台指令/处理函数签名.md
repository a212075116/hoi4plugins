# 处理函数签名

> 依据：capture_commander / bop_set / debug_zoom 三个 handler 的对照分析

## 真实签名是两个参数

    long long __fastcall handler(CmdResult* out, CmdArgs* args);

| 参数 | 偏移 | 含义 |
|---|---|---|
| out->ok | +0x00 | 1 = 成功 |
| out->message | +0x08 | 回显给玩家的 CString |
| args->data | +0x00 | CmdString*（元素是 CmdString 本身） |
| args->capacity | +0x08 | |
| args->count | +0x0C | **参数个数** |

## 决定性证据：capture_commander

sub_140241DF0 的签名是 __int64 __fastcall sub_140241DF0(__int64 a1, __int64 *a2)，
函数体里：

    if ( (unsigned int)(*((_DWORD *)a2 + 3) - 2) > 1 )        // a2+0x0C = count
    {
        Usage = "Usage: capture_commander <capturer_tag> <leader> [province_id]";
    }
    sub_1410E10C0(&v51, *a2);                                  // a2+0x00 = data[0]

count 必须落在 2..3，与该命令的 Usage 文本严格吻合。

bop_set 的 handler sub_1402856A0(__int64 a1, int *a2) 同样是两个参数。

## 为什么 debug_zoom 只写一个参数

sub_140250340(__int64 a1) —— **不是签名不同，是它不用参数**。
x64 下多余的参数就放在 rdx 里，函数不声明也能被调到。

## 参数元素的类型（运行时实证）

**这是最反直觉的一处。** args->data 是 CmdString*，
**元素就是 CmdString 本身（值语义）**，不是 CmdString**。

早期把它当二级指针解引用，读出来的"地址"其实是字符串的 ASCII 字节：

    输入 setcamheight 1    -> data[0] 头 8 字节 = 0x31       = '1'
    输入 setcamheight 50   -> data[0] 头 8 字节 = 0x3035     = "50"
    输入 setcamheight 355  -> data[0] 头 8 字节 = 0x353533   = "355"

所以永远读不到内容（IsReadable 判定 0x31 不可读）。

改正后：

    [setcamheight] args=... data=... capacity=1 count=1
       [0] elem=... size=1 cap=15 buf8=35 00 00 00 00 00 00 00
       [0] ArgToString=1 text="5"
    [setcamheight] h 310.00 -> 50.00 (arg="5" range [50,3000])

## CmdResult 的初始化责任在 handler

debug_zoom 的 handler 开头自己做了：

    *(_BYTE *)a1 = 0;
    *(_OWORD *)(a1 + 8) = 0LL;
    *(_QWORD *)(a1 + 24) = 0LL;
    *(_QWORD *)(a1 + 32) = 15LL;
    *(_BYTE *)(a1 + 8) = 0;

即把 message 置为合法空串。**handler 必须自己做这件事**，
这就是 ConsoleCmd_InitResult 存在的理由。
