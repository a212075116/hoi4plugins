# 避坑记录

本工程在"注册控制台指令"这件事上踩过的全部坑，按时间顺序。
**每一条都是真实发生过的崩溃或误判，不是假想。**

## 坑 1：CmdString 少写了 16 字节 SSO 缓冲

最初写成 {char* ptr; size_t size; size_t cap;} = 24 字节，
而真正的 MSVC std::string 是 32 字节。

后果：sizeof(ConsoleCommand) 变成 **352** 而不是 456，整个表项布局错位。

**发现方式**：加了一行日志打 sizeof，才看到 352。

**修正**：补上 union { char buf[16]; char* ptr; } 并加编译期断言。

## 坑 2：长字符串按 SSO 往 16 字节缓冲 memcpy

改好坑 1 后，描述串 "Set the camera height to the value given by sethcam_set"
有 56 字符，仍走 SSO 分支。

后果：memcpy 越过 32 字节的结构，**直接冲垮紧随其后的 +0x68 handler 函数指针**，
游戏当场崩。

**修正**：FillCStr 硬截断到 15 字符。

## 坑 3：同类错误再犯一次（SetMsg 放行到 127）

改好 FillCStr 后，SetMsg 里仍是 while (str[n] != 0 && n < 127) ++n;。

后果：**在控制台只输入命令名、直接回车**时，无参分支那条
"Currently,Camera Height is ..."（当时是 43 字符）把它写穿了，游戏又崩一次。

**这一条最值得记住**：修了一个越界点不等于修完了所有越界点。
凡是往 CString 里写东西的地方都要按 15 字符设限。

**修正**：SetMsg 也硬截断，并且所有面向玩家的短消息改成 <= 15 字符，
长消息统一走 sub_140129CA0。

## 坑 4：把 args->data 当成二级指针

看反编译时 IDA 把它推断成 __int64 *a2，我就当成 CmdString** 去解引用。

后果：读出来的"地址"其实是字符串的 ASCII 字节（0x31 = '1'），
IsReadable 判定不可读，**参数永远取不到**，而且不报错、不崩溃，
只是静默走"无参"分支 —— 最难查的一类问题。

**发现方式**：把所有候选项都 dump 出来看，才发现头 8 字节是 ASCII。

**修正**：CmdArgs.data 改成 CmdString*。

## 坑 5：源码含中文导致编译失败

MSVC 在无 /utf-8 时按系统代码页（936/GBK）解析源文件。

症状：

    warning C4819: 该文件包含不能在当前代码页(936)中表示的字符
    error C2001: 常量中有换行符

**修正**：源码全英文（含日志字符串）。生成脚本带非 ASCII 检查。

## 坑 6：carrier.def 的数据导出链接失败

     carrier.def : error LNK2001: 无法解析的外部符号 TBB_runtime_interface_version
     ... (共 11 个)
     fatal error LNK1120: 11 个无法解析的外部命令

原因：TBB_* 那批是**数据导出**，链接器不能为它们生成转发桩。
原 .bat 之所以能过，是先跑 lib /def: 生成导入库（那一步不校验符号），
再把 .exp 交给链接器。

**修正**：vcxproj 里用 BeforeTargets="Link" 的 Target 先跑 lib，见构建方式文档。

## 坑 5：把 int 字段当成字符串，游戏在 Tab 补全时崩

### 现象

用户在控制台按 Tab 触发补全时游戏崩溃。三次崩溃（16:17 / 17:37 / 17:49）
**地址完全相同**：`0x00007FF6F61763D3`（RVA `0x24B63D3`，在 `sub_1424B5EF0` 内）。

### 根因

崩溃点是 `strlen`：

    0x1424b63b0  mov  rdx, [rsi]
    0x1424b63d3  cmp  byte ptr [rdx+r8], 0

补全函数遍历命令表（步长 `v21 += 456`）：

    if ( *(int *)(entry + 0x28) > 0 )
        for (i = 0; i < *(int*)(entry + 0x28); i++)
            strlen( *(char**)(entry + 0x30 + i*8) );

**`+0x28` 是 `int aliasCount`、`+0x30` 是 `char* aliases[3]`，
而我把它当成 `usage` CString。**

写了 `usage = "<height>"` 之后，SSO 缓冲的前 4 字节 `<hei` 就是
`0x6965683C` = **1768253500**，补全函数于是循环 17 亿次，很快读到垃圾指针。

### 怎么定案的

1. 从注册日志里的 `merge 00007FF6F6174920` 反推 `base = 0x7FF6F3CC0000`
2. 算出崩溃 RVA `0x24B63D3`，看反汇编确认是 `strlen`
3. Frida dump 原版命令原始内存，看到 `+0x28` 取值只在 [0,3]，
   `+0x30` 起是 `char*` 指向 `"adiplo"` / `"rt"` / `"mio.AddFunds"`
4. 全表 386 条统计：`+0x28` 分布 `0:301 1:75 2:5 3:2`，
   而 `1768253500:3` 恰好只有我们注册的三条

### 修正

    - CmdString usage;                     // 错
    + int         aliasCount;              // +0x28
    + int         p2C;                     // +0x2C
    + const char* aliases[CMD_MAX_ALIAS];  // +0x30 .. +0x48

`sizeof(CmdEntry)` 仍为 456（断言通过），desc / handler / argCount / args 位置不变。

### 教训

**IDA 反编译出的结构布局，只代表「某种自洽的解读」，不代表语义正确。**
`+0x28` 处放 32 字节的 CString 和放 4 字节 int + 24 字节指针数组，
在内存布局上都能自圆其说，但**一旦另一个函数用不同方式解释同一块内存，就会暴露**。
所以字段语义必须靠**跨函数交叉验证**（本例是靠补全函数）才能定。

另外：**description 可以有 100+ 字符**（原版就有），走游戏的堆分配，
不能像早期那样一刀切限制 15 字节。

## 方法论收获

| 教训 | 说明 |
|---|---|
| 尺寸错误要用编译期断言兜住 | 否则一路错到运行时才崩 |
| 越界写要一次找全，不能只修一处 | 坑 2 与坑 3 是同一个错误 |
| 静态分析出来的类型不可全信 | IDA 的 `__int64*` 推断误导了我（坑 4） |
| 读不到数据时要 dump 原始字节 | 否则会在「类型不对」上绕圈 |
| 自检要在写内存之前 | 注册器先检查再写，实测拦住了真实错误 |
| **结构布局要靠跨函数交叉验证** | 单看构造序列会漏（坑 5） |
| **崩溃地址要换算成 RVA 再查** | 三次同地址即刻说明是同一 bug |
