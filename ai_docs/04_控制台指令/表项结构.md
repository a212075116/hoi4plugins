# 命令表项结构

> 依据：IDA 9.0 对 hoi4.exe 1.19.3 的静态分析
> 源码：src/plugin/console_cmd.h

## 表项 ConsoleCommand = 456 字节 (0x1C8)

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | int | flag（构造时写 1） |
| +0x04 | int | **未定**（构造时不写） |
| +0x08 | CString | **命令名** |
| +0x28 | CString | usage（用法提示） |
| +0x48 | CString | **描述** |
| +0x68 | void* | **处理函数指针** |
| +0x70 | void* | 0（8 字节） |
| +0x78 | void* | 0（8 字节） |
| +0x80 | int | **参数个数**（4 字节） |
| +0x84 | int | 0 |
| +0x88 | CString[10] | 参数名，每个 32 字节，共 320 |

0x88 + 0x140 = 0x1C8 = 456。

## 字段宽度怎么定死的

同一个构造序列里，四条清零指令的**操作码宽度不同**：

    0x1400097ad  48 89 85 88dc0000          mov [base+0x68], rax       8 字节 (handler)
    0x1400097b4  48 c7 85 90dc0000 0000..   mov qword [base+0x70], 0   8 字节
    0x1400097bf  48 c7 85 98dc0000 0000..   mov qword [base+0x78], 0   8 字节
    0x1400097ca  c7 85 a0dc0000 00000000    mov dword [base+0x80], 0   4 字节 (argCount)

48 c7 85 是 64 位写（MOV r/m64, imm32 符号扩展），c7 85 是 32 位写（MOV r/m32, imm32）。

**remove_core 的对应位置（0x1400096f4 / 0x1400096ff / 0x14000970a）字节完全一致。**

## 结构是怎么解出来的

对照两个不同命令的构造序列。以 debug_zoom（0x14000975c 处）
与 remove_core（0x14000969c 处）为例：

| 汇编动作 | debug_zoom | remove_core |
|---|---|---|
| mov [base+0x00], 1 | 1 | 1 |
| CString(base+0x08) | "debug_zoom" | "remove_core" |
| CString(base+0x28) | 空 | 空 |
| CString(base+0x48) | "Zooms in the game" | "Remove core" |
| mov [base+0x68], fn | sub_140250340 | sub_14027BC60 |
| mov [base+0x80], N | **0** | **1** |
| CString(base+0x88) | 空 | "<Province ID>" |

**+0x80 与参数个数严格对应**，这是结构解出的关键证据。

## 与析构函数交叉验证

sub_14022BE10（表项析构）：

    eh vector destructor iterator(a1 + 17, 0x20uLL, 0xAuLL, sub_14011EBD0)
    n0xF   = a1[12]   // +0x60 -> description 的 cap
    n0xF_1 = a1[4]    // +0x20 -> name 的 cap

- a1+0x88 起 10 个 32 字节元素 -> 参数数组；0x88 + 10*0x20 = 0x1C8
- a1[12]=+0x60 与 a1[4]=+0x20 分别落在 name（+0x08+0x18）与 description（+0x48+0x18）的 cap 上

两条独立路径（构造 / 析构）结论一致。
