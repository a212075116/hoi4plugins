# 命令表项结构

> 依据：IDA 9.0 静态分析 + Frida 运行期 dump（2026-10-09 修正）
> 源码：src/plugin/SDK_RVA/console/console_cmd.h

## 表项 ConsoleCommand = 456 字节 (0x1C8)

| 偏移 | 类型 | 含义 |
|---|---|---|
| +0x00 | int | flag（构造时写 1） |
| +0x04 | int | **未定** |
| +0x08 | CString | **命令名** |
| **+0x28** | **int** | **别名个数 aliasCount** |
| +0x2C | int | 未定（dump 里常见非 0 残留） |
| **+0x30** | **const char\*[3]** | **别名/缩写数组**（24 字节，到 +0x48） |
| +0x48 | CString | **描述** |
| +0x68 | void* | **处理函数指针** |
| +0x70 | void* | 未定 |
| +0x78 | void* | 未定 |
| +0x80 | int | **参数个数** |
| +0x84 | int | 0 |
| +0x88 | CString[10] | 参数名，每个 32 字节，共 320 |

0x88 + 0x140 = 0x1C8 = 456。

## 修正说明：+0x28 不是 usage，是别名个数

**早期把 `+0x28` 当作 `usage` 字符串，这是错的，并直接导致游戏在
Tab 补全时崩溃。**

### 怎么发现错的

控制台补全函数 `sub_1424B5EF0` 会遍历命令表（步长 `v21 += 456`），对每条命令：

    if ( *(int *)(entry + 0x28) > 0 ) {
        v29 = (char **)(entry + 0x30);
        for (i = 0; i < *(int*)(entry + 0x28); i++) {
            strlen(v29[i]);          // <- 崩在这里
        }
    }

它把 `+0x28` 当**循环次数**、`+0x30` 起当 **char\* 数组**。

如果 `+0x28` 处放的是 SSO 短字符串，其前 4 字节就是字符内容：

    usage = "<height>"  ->  *(int*)(+0x28) = 0x6965683C = 1768253500
    -> 补全函数循环 17 亿次 -> 读到垃圾指针 -> strlen 崩溃

崩溃地址三次完全相同（`0x24B63D3`），与 Tab 补全操作一一对应。

### 原版命令的实际数据（Frida dump）

    allowdiplo        +0x28=2  +0x30 -> "adiplo"        +0x38 -> "nocb"
    reload_textures   +0x28=2  +0x30 -> "rt"            +0x38 -> "reload_texture"
    AddFunds          +0x28=2  +0x30 -> "mio.AddFunds"  +0x38 -> "IndustrialOrganisation.AddFund"
    faction_initiative +0x28=1 +0x30 -> "fi"
    debug_zoom        +0x28=0  （无别名）

全表 386 条的 `*(int*)(+0x28)` 分布：

    0 -> 301   1 -> 75   2 -> 5   3 -> 2

取值全在 [0,3]，而 `+0x30` 到 `+0x48` 正好能放下 3 个指针 ⇒ 数组容量 3。

## 字段宽度怎么定死的（仍然有效）

同一个构造序列里，四条清零指令的**操作码宽度不同**：

    0x1400097ad  48 89 85 88dc0000          mov [base+0x68], rax       8 字节 (handler)
    0x1400097b4  48 c7 85 90dc0000 0000..   mov qword [base+0x70], 0   8 字节
    0x1400097bf  48 c7 85 98dc0000 0000..   mov qword [base+0x78], 0   8 字节
    0x1400097ca  c7 85 a0dc0000 00000000    mov dword [base+0x80], 0   4 字节 (argCount)

`48 c7 85` 是 64 位写，`c7 85` 是 32 位写。remove_core 的对应位置字节一致。

## 与析构函数交叉验证

`sub_14022BE10`（表项析构）：

    eh vector destructor iterator(a1 + 17, 0x20uLL, 0xAuLL, sub_14011EBD0)
    n0xF   = a1[12]   // +0x60 -> description 的 cap
    n0xF_1 = a1[4]    // +0x20 -> name 的 cap

- `a1+0x88` 起 10 个 32 字节元素 ⇒ 参数数组；`0x88 + 10*0x20 = 0x1C8`
- `a1[12]=+0x60` 与 `a1[4]=+0x20` 落在 `name`（`+0x08+0x18`）与 `description`（`+0x48+0x18`）的 cap 上

**注意析构只处理 name / description / args —— 没有 usage，这本身就是个旁证。**
别名是指向 DLL 里常量字符串的裸指针，不归表项所有，所以不需要析构。

## 字符串长度

| 字段 | 长度限制 |
|---|---|
| name / description / args | **无限制**（超 15 字节时走游戏的 `sub_140129CA0` 堆分配） |
| alias | 无限制（只是裸指针） |

实测原版 description 有 100+ 字符的（如 `faction_initiative`）。

`ConsoleCmd_SetMessage` / `WriteStr` 已按此实现。
