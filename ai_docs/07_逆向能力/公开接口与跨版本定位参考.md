# 公开接口与跨版本定位参考

核对日期：2026-10-14。范围：公开的一手资料，不代替当前游戏二进制实测。

## 先区分三个问题

1. **官方支持的原生接口**：厂商定义对象取得方式、函数签名、生命周期与版本协商。
2. **内部对象和虚表定位**：从 RTTI、注册表、构造函数等恢复地址，不等于厂商承诺 ABI 稳定。
3. **自建兼容层**：把不稳定的游戏内部绑定封装到插件自己的稳定接口后面，减少升级修改面。

公开资料能确认 Source 的第一类机制和 HOI4 的脚本扩展能力；不能仅凭检索结果断言 HOI4 所有模块、所有版本都不存在内部接口工厂。

## Source 的 CreateInterface 真正解决了什么

Valve 头文件规定接口以纯虚函数和无数据成员的形式发布；调用者使用共享接口声明和版本名取得实现对象。
接口工厂返回的是对象指针，不是“任意类虚表查询器”。实现可以有多继承，工厂负责返回相应接口视图。[Valve interface.h](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/tier1/interface.h)

实现遍历注册链表，按接口名字精确匹配后调用构造回调；找不到就返回空指针并设置失败状态。
因此必须先存在注册及公开合同，单纯存在虚表不会自动获得工厂服务。[Valve interface.cpp](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/tier1/interface.cpp)

头文件也明确区分兼容地追加方法与不兼容修改：后一种需要新版本名，并由实现者提供旧接口包装层。
**结论：跨版本兼容依靠接口提供方维护，不是 CreateInterface 这个名字自带的保证。**
该结论来自公开版本规则，而非对 HOI4 是否存在同类工厂的证明。[Valve 版本规则](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/tier1/interface.h#L16-L24)

## HOI4 官方公开扩展能力：已证实与未证实

官方开发日志明确介绍通过软编码、场景脚本和配套工具提供 modding，能证实的是数据／脚本侧扩展。
这篇早期资料不能证明 2026 年的所有能力边界，也不能用来证明内部原生工厂绝对不存在。[官方开发日志 52](https://store.steampowered.com/news/posts/?appids=394360&enddate=1461329442)

后续官方日志继续公开脚本修饰符、效果／触发器、GUI、本地化及调试工具等扩展点；这与发布 C++ 类布局、虚表槽位和对象寿命保证是两回事。[官方 modding 开发日志](https://store.steampowered.com/news/posts/?appids=394360&enddate=1582584245)

本次检索**未取得**面向 HOI4 游戏内核、类似 Valve 版本化 C++ 接口工厂的公开合同。
准确结论是“尚未建立可依赖的官方原生 ABI 证据”，不是“数学证明不存在任何接口”。
导出表里没有特定名字，只能排除那个映像以那个名字直接导出的情况；不能排除内部注册表、其他模块、序号导出或不同命名。
这些属于证据边界分析，不是新增发现某个 HOI4 隐藏接口。

## 修正 x64 RTTI 的重要误解

LLVM 的 Microsoft ABI 实现对 64 位目标启用 image-relative RTTI：COL 的类型描述符、类层级描述符、自引用字段使用 32 位映像相对值。
它们不是普通 64 位绝对指针；这是常规 Microsoft x64 ABI 行为，不能据此称 HOI4 使用特殊 RTTI 格式。[LLVM 结构生成代码](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/MicrosoftCXXABI.cpp#L454-L547)

COL 本身通常是六个 32 位字段，签名为 1；类型描述符等地址按映像基址加字段 RVA 解析。
LLVM 的 x64 测试直接核对该输出。[LLVM RTTI 测试](https://github.com/llvm/llvm-project/blob/main/clang/test/CodeGenCXX/microsoft-abi-rtti.cpp)

不要与虚表前缀混淆：正常带 RTTI 的 x64 虚表，其首个虚函数之前的 `vftable[-1]` 是指向 COL 的 64 位指针。
LLVM 将虚表地址点设在 RTTI 指针之后；内部 32 位 RVA 与这里的 64 位指针并不矛盾。[LLVM 虚表地址点生成](https://github.com/llvm/llvm-project/blob/main/clang/lib/CodeGen/MicrosoftCXXABI.cpp#L1773-L1793)

这是编译器 ABI 实现证据；具体 HOI4 类是否保留 RTTI、有几个子对象虚表、哪个表对应所需接口，仍需当前映像验证。

## 对我们项目的工程推论

| 目标 | 可行路线 | 不能承诺 |
|---|---|---|
| 快速找到虚表 | 类型名 → TypeDescriptor → COL → 虚表交叉引用，结合节区与多继承校验 | 名字存在就唯一、槽位语义永远相同 |
| 降低升级成本 | 保持插件侧稳定接口，游戏绑定放入独立版本适配层 | 自建接口反过来使游戏 ABI 稳定 |
| 减少手工改 RVA | 组合 RTTI、注册名称、字符串交叉引用、指令语义／调用图、版本差分 | 单一字节签名永久有效 |
| 防止错绑运行 | 多证据唯一匹配、布局与合同校验、功能级失败关闭、已知版本缓存 | 自动迁移结果可以未经验证直接调用 |

上表是工程建议，不是已经落地或在两个游戏版本上验证的功能。
找回地址只能解决“在哪”；还要核对“是什么、怎么调用、由谁释放、何时有效”。
下一版若仅发生重排，自动定位有机会直接复用；若签名、字段或语义改变，仍需更新适配层。
合理目标是让升级主要变为差异审查与回归，而不是每次从零逆向；不存在对未知未来版本无条件安全运行的技术保证。

## 证据 → 发现 → 后续路径

- Valve 源码 → 工厂需版本化合同 → 借鉴接口边界，不照搬“有工厂就永久兼容”的判断。
- HOI4 官方日志 → 确认脚本扩展，原生 ABI 证据未建立 → 结合本地全部相关模块检验，结论保持限定范围。
- LLVM 实现与测试 → x64 COL 内部 RVA 是正常 ABI → 修正文档，再验证当前映像的 RTTI／虚表定位可用性。
- 自建适配层建议 → 可降低地址变动传播面 → 用至少两个已知游戏构建做离线迁移评估，再谈跨版本成功率。
