## 错误标记拒绝矩阵

每例先构造匹配原侧车的中断状态：generation=5、元素低位=7、receipt存在；随后仅破坏一个检查条件。
公开恢复拒绝后，检查隔离查询为false、低位仍为7、generation仍为注入值；然后恢复那个检查条件，再调用公开恢复并核对值与长度。
保留字段修改属于测试故障注入，不是提供给模组作者的正常修复流程。

| 单项故障 | 预期状态 | 接下来的操作 |
|---|---:|---|
| nonce n0错误 | -5 | 还原精确nonce后恢复 |
| receipt phase错误 | -5 | phase还原为1后恢复 |
| receipt n2缺失 | -5 | 补回本对象的精确receipt后恢复 |
| branch b0错误 | -7 | 还原本对象归属后恢复 |
| incarnation i0错误 | -7 | 还原本对象实例标记后恢复 |
| generation为另一个奇数7 | -6 | 还原意图对应奇数5后恢复 |
| 原生容器identity id2缺失 | -902 | 还原原始身份后恢复 |

国家ABY、ARI、州335、角色ABY_Hoshino、global均执行上述七例，共35个单项拒绝场景。
修正故障后恢复到 [12345678901.125]、长度1；不是把错误标记替换为任意新标记。
另将五份同名prf侧车循环放入另一个scope目录，恢复返回-1，健康数组的值、长度、generation保持不变；恢复原侧车字节后继续。

## 保存错误状态再重启

每scope同时注入错误nonce和错误branch，保存l64bad后退出并重启。
先恢复返回-5；只修正nonce，再恢复返回-7；最后修正branch，恢复返回0并核对完整精度。
这证明读档后检查顺序仍生效，不会因为进程地址变化或缺少一次运行时上下文而绕过归属检查。
该用例仍是模拟故障状态，不是随机强杀进程、断电或文件写入中断。

## 旧存档与最新侧车

1. 先将健康基线 [12345678901.125]、generation=6 保存为l64old。
2. 不再保存游戏，公开set_array_element64写入2.5，generation变为8，并产生更新的侧车；记录五份新侧车哈希。
3. 退出并仅用-continuelastsave重启旧存档。它包含旧值和generation=6，但文件系统中仍是更新的意图。
4. recover_array64返回-5；旧值、长度1和generation=6不变，不将2.5或另一份基线强塞入旧存档。
5. 将原始配对侧车逐字节恢复，再调用recover_array64返回0，值、长度和generation不变。

这里只证明所列配对状态的保守拒绝/接受，不提供自动历史日志检索或复制存档自动fork识别。
最新侧车只能描述最近操作，旧存档必须由用户保留配对备份；不要手工修nonce/owner字段绕过检查。
恢复返回非0也不一定意味着健康数组坏了：它可能只是与当前文件系统中的最新意图不配对。
