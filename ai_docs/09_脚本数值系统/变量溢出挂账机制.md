## 一、要解决的问题

32 位变量与 64 位变量做加减, 结果超出 int32 范围时, 若直接写回槽会回绕成错误值。
挂账机制把这部分差额先记账, 后续用加法逐步抵消。

## 二、规则

```
挂账不存在 + 结果超 int32 -> 变量锁【可显示的极值】, 差额全额计入挂账
挂账存在 -> 任何加减只抵扣挂账, 变量值不动 (字面量与变量操作数都支持)
挂账 >= 0 -> 结算: 变量 = 锁定值 + 剩余挂账 (用 raw 直接相加, 精确)
```

## 三、数据结构

```c
typedef struct {
    char      name[40];

```

## 四、两个必须记住的技术点

### 4.1 锁定值不能用精确的 int32 边界

用 `-2147483648` 会让**游戏自己的定点格式化出错**, 显示成 `--2147483648`。
原因是它在计算 `|raw|/100000 = 2147483648` 时超出 int32 正范围。

改用**游戏能正确显示的极值**:

```
负溢出 -> -2147483647.99999   (raw = -214748364799999 = INT32_MIN * 100000 + 1)
正溢出 ->  2147483647.99999   (raw =  214748364799999)
```

差的那 0.00001 那一档**全额计入挂账**, 所以数学上仍然精确 (见第六节实测)。

### 4.2 挂账变量的判断不能只看 64 位登记表

```c
if (debt == NULL && Var64_IsSixtyFourBitName(name)) return 0;
```

即: **只要这个变量身上有挂账, 无论它是否登记过, 都必须走抵扣路径**。
早期写成 `if (IsSixtyFourBitName(name)) return 0;` 会让抵扣被跳过。

## 六、一个曾经误判的结论 (记录以免重犯)

首轮测试时算出 `-1499996900` 与手算的 `-1500000000` 差 3100, 我一度当成 bug。
后来日志逐项打印证明: 真实结果本来就是 `-1499996900`
(`100 - 5000000000 + 1000 + 2000 + 2500000000 + 1000000000`), 是我手算漏加。
**教训**: 怀疑数值错误时, 先把每个中间量打出来, 不要凭心算下结论。
