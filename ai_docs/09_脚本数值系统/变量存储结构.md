# 游戏变量的存储结构（查证 + 实测验证）

> 上游：变量怎么被找到（token → entry → 工厂 → 虚表 → exec）见同目录《set_variable执行路径.md》。
> 本文只讲存储本身：哈希表、节点布局，以及用 CE 做的实测验证。
## 七、变量存储结构（第2轮追加 · 完全解密）

### 7.1 源文件位置

变量系统核心在 `hoi4\source\scopedvariable.cpp`（断言里给出的路径，行号 1430/1431）。

两条断言：

- `IsReadOnly() == false`
- `pVariables != nullptr && "invalid event scope to get variable"`

### 7.2 变量容器定位

`sub_140542330` 里 `v4 = *(_QWORD *)(a1 + 160)` —— **实例的 `+160` 就是变量容器指针**。
（注意：参数 `a4` 非 0 时优先用 `a4`。）

哈希表本体在 **容器 `+16`**（`sub_140BC5C10` 里 `v4 = a1 + 16`）。

### 7.3 查找算法 = FNV-1a 32 位

```c
v7 = -2128831035;                       // 0x811C9DC5  FNV offset basis
do {
    v9 = *v5++;
    v7 = 16777619 * (v7 ^ v9);          // 0x01000193  FNV prime
} while (--v8);
```

就是标准 FNV-1a。**这意味着我们可以自己算 hash，不依赖游戏函数。**

### 7.4 哈希表结构

`sub_140BC3F10(表, 出参, hash, 名字对象, a5)`：

| 表内偏移 | 内容 |
|---|---|
| `+8` | 桶数组基址 |
| `+16` | 元素数（`*(_DWORD *)(a1 + 16)`） |
| `+20` | **桶掩码**（容量-1，`hash & mask` 定位桶） |
| `+24` | byte 阈值（`v7 > *(_BYTE *)(a1 + 24)` 触发扩容判断） |
| `+28` | float 装载因子 |

桶步长 **48 字节**：`v10 = *(QWORD*)(a1 + 8) + 48 * (hash & mask)`。
桶内遍历：`v10 += 12`（12 个 DWORD = 48 字节）跳到下一条目。

### 7.5 条目（节点）结构 —— 48 字节

| 节点内偏移 | 内容 |
|---|---|
| `+0` | hash（4 字节） |
| `+4` | byte：桶内条目序号 |
| `+8` | **std::string 变量名**（SSO 布局：data `+8`、size `+24`、cap `+32`） |
| **`+40`** | **值（8 字节）** |

命名比较逻辑（原文）：

```c
Buf2 = v10 + 2;
if ( *((_QWORD *)v10 + 4) > 0xFuLL ) Buf2 = *(unsigned int **)Buf2;   // cap > 15 走间接
if ( Buf1[1] == *((void **)v10 + 3) && (!Buf1[1] || !memcmp(Buf1[0], Buf2, Buf1[1])) )
    break;                                                             // 名字命中
```

`v10+2`（DWORD）即 `+8`；`*((QWORD*)v10 + 4)` 即 `+32`（cap）；
`*((void**)v10 + 3)` 即 `+24`（size）。

### 7.6 值地址 = 节点 + 40

`sub_140BC5C10` 最后一行就是 `return v11 + 40;` —— **值就是节点内的一个 8 字节字段**。

        │           ├─ sub_1405454A0(...)      构造变量名 std::string

## 九、对实现的意义

**我们现在有两条路可以读写游戏变量**：

| 路线 | 做法 | 优缺点 |
|---|---|---|
| A. 调游戏函数 | 造一个 `CSetVariableEffect` 实例，填好变量名，调 `sub_140542280` 拿地址 | 稳，但依赖实例构造细节 |
| B. 自己实现 | 从容器指针出发，用 FNV-1a 算 hash，遍历桶找节点，取 `+40` | **不需要构造实例**，逻辑已完全掌握 |

**路线 B 更干净** —— hash 算法、桶定位、节点布局都已知，
只需拿到「变量容器指针」，而它就在 `实例 + 88 + 160`。
要拿到容器，可以调 `sub_140542280` 或直接找到当前作用域的容器来源。

## 十一、实测验证（第2轮 · CE 动态）

### 11.1 实验方法

1. mod 事件里设两个变量：

```
set_variable = { dshprobe = 1847293651 }                             # 简写形式
set_variable = { var = dshprobe2 value = 1234567891 }                 # 完整形式
```

两种形式**都成功**（`game.log` 里读回 `1847293651` 和 `1234567891`）。

2. 定点换算：`1847293651 x 100000 = 184729365100000`（8 字节）。

3. 用 CE `scan_all` 扫这个 8 字节值 → **命中 2 个地址**：

```
0x2206B2ECEF8   184729365100000
0x2207EEEA598   184729365100000
```

### 11.2 节点布局实测（第一个地址周围）

以值地址 `a = 0x2206B2ECEF8` 为原点，读 8 字节视角：

| 偏移 | 值 | 解释 |
|---|---|---|
| `-40` | `0x4B81F1142` | 节点 +0：hash（低 32 位 `0xB81F1142`） |
| `-36` | `4` | 节点 +4：桶内条目序号/总数 |
| `-32` | `0x65626F7270687364` | **节点 +8：`"dshprobe"`**（小端 ASCII） |
| `-24` | `0` | 节点 +16：SSO 数据尾 |
| `-16` | `8` | 节点 +24：size = 8（正好是 `dshprobe` 的长度） |
| `-8` | `15` | 节点 +32：cap = 15（SSO 上限） |
| `0` | `184729365100000` | **节点 +40：值** |

`0x65626F7270687364` 按小端拆字节：

```
64 73 68 70 72 6F 62 65
 d  s  h  p  r  o  b  e    => "dshprobe"
```

**与静态分析推断的节点布局逐项吻合。**

### 11.3 FNV-1a 哈希验证

手算（Python）：

```python
h = 0x811C9DC5
for ch in b'dshprobe':
    h = (h ^ ch) * 0x01000193 & 0xFFFFFFFF
```

结果：

```
FNV-1a(dshprobe) = 0xB81F1142 = 3089043778
内存实测节点+0    = 0xB81F1142 = 3089043778
MATCH
```

**哈希算法完全确认，且能自己算，不依赖游戏函数。**

## 十四、`CScopedVariable` 类的布局（第3轮）

### 14.1 类名来源

`CSetVariableEffect` 实例 `+88` 处的子对象，其构造函数是 `sub_14014AFD0`：

```c
__int64 __fastcall sub_14014AFD0(__int64 a1)
{
    *(_DWORD *)(a1 + 8)  = 256;                        // ★ 哈希表容量
    *(_DWORD *)(a1 + 16) = 0;
    *(_QWORD *)a1 = &CScopedVariable::`vftable';      // ★ 类名
    *(_WORD *)(a1 + 20) = 0;  *(_WORD *)(a1 + 12) = 0;
    *(_BYTE *)(a1 + 14) = 0;  *(_DWORD *)(a1 + 24) = 0;
    *(_QWORD *)(a1 + 32) = 0; *(_QWORD *)(a1 + 40) = 0;
    *(_DWORD *)(a1 + 48) = 0;
    *(_DWORD *)(a1 + 52) = 19479;   *(_DWORD *)(a1 + 56) = 19479;
    *(_QWORD *)(a1 + 64) = 0; *(_QWORD *)(a1 + 72) = 0; *(_QWORD *)(a1 + 80) = 0;
    sub_14011DF40((void *)(a1 + 88));                 // std::string 构造
    *(_OWORD *)(a1 + 112) = 0;                        // std::string（SSO）
    *(_QWORD *)(a1 + 128) = 0;
    *(_QWORD *)(a1 + 136) = 15;                       // cap = 15
    *(_BYTE *)(a1 + 112) = 0;
    *(_QWORD *)(a1 + 144) = 0;
    *(_BYTE *)(a1 + 152) = 0;
    *(_QWORD *)(a1 + 160) = 0;                        // 另一个指针（父/容器）
    *(_QWORD *)(a1 + 168) = 0;
    *(_OWORD *)(a1 + 176) = 0;                        // std::string（SSO）
    *(_QWORD *)(a1 + 192) = 0;
    *(_QWORD *)(a1 + 200) = 15;                       // cap = 15
    *(_BYTE *)(a1 + 176) = 0;
}
```

### 14.2 已知字段

| 偏移 | 初值 | 推断 |
|---|---|---|
| `+0` | 虚表 | `CScopedVariable::vftable` |
| `+8` | **256** | **哈希表容量**（⇒ mask = 255） |
| `+12` | 0（word） | 标志 |
| `+14` | 0（byte） | **标志**（`sub_140542280` 里 `*(BYTE*)(a1+14)` 决定分支） |
| `+16` | 0 | 元素数 |
| `+20` | 0（word） | 标志 |
| `+24` | 0 | 计数 |
| `+32` / `+40` | 0 | 指针 |
| `+48` | 0 | 计数 |
| `+52` / `+56` | **19479** | 常量（疑似 token id） |
| `+64` / `+72` / `+80` | 0 | 指针 |
| `+88` | std::string | 由 `sub_14011DF40` 构造 |
| `+112` | std::string | SSO，size `+128`，cap `+136`=15 |
| `+144` | 0 | 指针（`sub_1405454A0` 里用 `a1+144`） |
| `+152` | 0（byte） | 标志 |
| **`+160`** | **0** | **指针**（`sub_140542330` 里作为容器候选） |
| `+168` | 0 | 指针 |
| `+176` | std::string | SSO，size `+192`，cap `+200`=15 |

### 14.3 哈希表的真实位置

重新核对两个函数的偏移：

```c
// sub_140BC5C10(int a1, ...)   a1 = 容器
v4 = a1 + 16;                              // 表 = 容器 + 16
sub_140BC3F10(v4, &v11, hash, name, id);
return v11 + 40;                           // 值 = 节点 + 40

// sub_140BC3F10(__int64 a1, ...)   a1 = 表
v6  = *(int *)(a1 + 20);                   // mask
v10 = *(QWORD *)(a1 + 8) + 48 * (hash & v6);  // 桶数组 = *(表 + 8)
```

**结论**：

| 项 | 位置 |
|---|---|
| 容器 | `CScopedVariable`（或它的 `+160`） |
| 表 | 容器 + 16 |
| 桶数组指针 | `*(表 + 8)` = `*(容器 + 24)` |
| mask | `*(表 + 20)` = `*(容器 + 36)` |
| 桶步长 | 48 字节 |
| 值 | 节点 + 40 |

### 14.4 一个重要的否定结论

**桶数组是独立分配的内存**（`*(表+8)` 是一个指针，不是内联数组）。
所以**无法从节点地址反推容器地址** —— 这条路走不通。

实测验证：按「桶数组内联、容量 256」假设算出的容器地址 `0x2206B2EC1D0`，
CE 读取时脚本异常，说明该地址不成立。

### 14.5 exec 里容器的真实来源

```c
sub_140364C60(a1=实例, a2=ctx)
  v4 = sub_140542280(a1 + 88, a2, 0);         // 返回【值的地址】

sub_140542280(a1=CScopedVariable*, a2=ctx, a3=0)
  if (*(BYTE*)(a1 + 14)) v6 = sub_14054F730();
  else                   v6 = sub_140542500(a1, a2, &v15, &v14, ...);   // ★ 642 行
  return sub_140542330(a1, v6, a2, a3);

sub_140542330(a1=CScopedVariable*, a2=v6, a3=ctx, a4=0)
  if (!v4) v4 = *(QWORD*)(a1 + 160);
  sub_1405454A0(a1, v15, a3, v4);            // 造变量名
  ...
  v11 = sub_140BC5C10(a2 /*= v6*/, v14, v9); // ★ 容器 = v6
```

**容器 = `v6`，由 `sub_140542500`（642 行的作用域解析）产出。**
`CScopedVariable + 160` 是另一条候选路径。

## 十五、effect 的 scope 是什么（第4轮 · 诊断实测）

### 15.1 诊断手段

写了一个诊断 effect `var64_diag`，在 exec 里把 `self`（effect 实例）和 `scope`（作用域）
的指针字段全部打进插件日志（只打印「指向可读内存」的字段，避免打印纯数值）。

代码位置：`src/plugin/SDK_RVA/variable64/variable64.c` 的 `ExecVar64Diag`。

### 15.2 scope 的类型 = `CEventScope`

`scope + 0` 是虚表指针。用 CE 拿到运行期地址后，
按 RTTI 定位器 → type_info 的路径解析出类名：

```
scope+0            = 0x7FF6C88A43E8        (虚表)
虚表-8             = 0x142C23A80           (RTTI 定位器)
定位器.pTypeDesc   = 0x030CC268  →  type_info @ 0x1430CC268
type_info+16       = ".?AVCEventScope@@"
```

**scope 是 `CEventScope`（事件作用域）。**

### 15.3 实测字段（一次典型调用，地址随运行变化）

| 偏移 | 值 | 说明 |
|---|---|---|
| `+0x000` | `0x7FF6C88A43E8` | **虚表**（CEventScope） |
| `+0x008` | `DCE7CC8900000003` | 数值，非指针 |
| `+0x010` | `000000008C120EFC` | 数值 |
| `+0x018/0x020/0x028` | 指向 `scope+0x18` | **自引用**（链表哨兵） |
| `+0x030/0x038` | 0 | |
| `+0x0B0` | `0x7FF6C88A43E8` | **同一个虚表**（内嵌的第二个 CEventScope） |
| `+0x0C8/0x0D0/0x0D8` | 指向 `scope+0xC8` | 自引用 |
| `+0x160` | `0x7FF6C8C61D08` | 另一个虚表 |
| `+0x168` | `0x7FF6C87F0B08` | 另一个虚表 |

**`CEventScope` 是个「大对象内含多个子对象」的结构**（至少 4 个虚表：`+0`、`+0xB0`、`+0x160`、`+0x1E8`）。

### 15.4 否定结论：这些候选都不是变量容器

判断标准：真容器的 `mask`（表 `+20`）必须是 `2^k - 1`（构造函数里容量初值 256 ⇒ mask 255）。

| 候选 | buckets | mask | 判定 |
|---|---|---|---|
| `scope` | `= scope` | **4** | ✗ 不是 2^k-1 |
| `scope+0x1C8` 指向 | 垃圾 | 7209061 | ✗ |
| `scope+0x1E0` 指向 | 13 | 0 | ✗ |
| `scope+0x160` 指向 | — | 32758 | ✗ |
| `scope+0x168` 指向 | — | 32758 | ✗ |
| `self+0x130` 指向 | — | 0 | ✗（这一项其实是 SSO 字符串数据） |

**在 `scope` 里用我们的算法查 `dshprobe` 全部失败。**

### 15.6 下一步（第5轮）：造一个 CSetVariableEffect 实例

`scope` 这条路已经证明走不通（变量表不在我们能猜到的偏移上）。
**更可靠的做法是直接复现游戏自己的调用链**：

```c
/* 工厂地址已知：RVA 0x341F60 */
void* inst = ((void* (*)())(img + 0x341F60))();   /* 造 CSetVariableEffect，malloc 0x220 */
/* 变量名写到 inst + 512（std::string，SSO，cap 在 +536） */
/* 然后调 exec 的取值路径：sub_140542280(inst + 88, scope, 0) 拿值地址 */
/* 或者干脆填好参数后调 exec 本体 sub_140364C60(inst, scope) */
```

**注意**：`sub_140364C60` 读参数用的是 `sub_140544C90(inst+296, &v, ctx, 0, 1)`，
第 5 个参数是 **1**（我们一直传 0）。要复现必须照传。

另一条更省事的路径：既然 `CScopedVariable` 在 `inst + 88`，而 `sub_140542280` 就是
「按名字取值的地址」，那么**造好实例、填好名字、直接调 `sub_140542280`** 即可，
不必碰参数读取。
