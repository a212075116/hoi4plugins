# 脚本变量的数值类型与上限

> 全部结论都有实测或静态证据，来源逐条标注。看不到证据的说法一律标为【推断】。

## 一句话结论

**脚本变量（`set_variable`）的值是 32 位有符号整数，上限 `2147483647`（2^31-1）。**
引擎里**另有** 64 位定点类型 `CFixedPoint64`，但脚本变量不用它。

## 历史：上限变过

| 时期 | 上限 | 原因 |
|---|---|---|
| 2026-05 之前 | **约 21.47M** | 变量用定点表示，scale 占掉 100 倍位宽 |
| 2026-05 之后（当前 1.19.3）| **2147483647** | 官方去掉定点小数，位宽全部给整数部分 |

**用户最早报告「最大只能上 21M」，是因为记忆停留在旧版本。** 这个变化是官方在
客户端更新里做的（用户核对确认）。

**这条历史本身就是重要证据**：官方在 32 位里重新分配位宽，而**没有**升到 64 位。

## 实测数据（方法：在 mod 事件里 set/add 变量并 `log`，从 `game.log` 读回）

### 边界

| 输入 | 读回 | 判定 |
|---|---|---|
| `2147483647` | `2147483647` | **OK，正好是上限** |
| `2147483648` | `-2147483648` | **翻负**（标准补码回绕） |
| `10000000000` (1e10) | `1410065408` | 截断，`1e10 mod 2^32 = 1410065408` 吻合 |
| `100000000000` (1e11) | `1215752192` | 截断，`1e11 mod 2^32 = 1215752192` 吻合 |
| `1e15` | `1197668250.4192` | 截断且出现小数 |

### 加法（正常）

    set 2, add 1000000 x26        -> 26000002        正常
    set 20000000, add 10000000 x5 -> 70000000        正常
    set 50000000, add 100000000 x5-> 550000000       正常（5.5 亿）

### 乘法（走定点路径）

    set 1000000
    multiply_variable = 100       -> 100000000         整数
    multiply_variable = 1000      -> 387582001.96842   出现 5 位小数
    divide_variable   = 1000      -> 387582.00196      5 位小数

**5 位小数 ⇒ 运算层仍是 `CFixedPoint`，内部 scale 为 100000。**
存储层是整数，运算层带定点语义，两者不是一回事。

### 复现方式（用户给出的方法，最省事）

```
# mod 的事件里
set_variable   = { test_number = 2147483648 }
log = "[?test_number]"
```
然后读 `logs/game.log`，搜 `effectbase.cpp:1783` 那行。

已建好的事件见 `test/modules/console/zz_numtest_events_reference.txt`（`.26`~`.29`），
触发脚本 `test/modules/console/numtest_trigger_events.py`。

## 静态分析证据

| 事实 | 证据 |
|---|---|
| 引擎有两个定点类型 | 断言 `"Conversion between CFixedPoint64 and CFixedPoint Failed, upper bounds / lower bounds"` |
| 64→32 转换是显式且会失败的 | `sub_1424ED580`，里面有 `(int)` 截断，失败分支 `__debugbreak()` |
| `CFixedPoint` 属引擎核心库 | 断言源路径 `clausewitz\pdx_core\fixedpoint.cpp` |
| 游戏知道变量会溢出 | `"Variable overflow! Please try fixing this function to avoid such things."` @ `sub_140E7AFE0` |
| 变量系统是模板化的，值类型写死在实例里 | `CVariableEffect` / `CVariableResolver` / `VCTempVariableResolver`，共 **44 个 `CVariable*` RTTI** |
| 定点转换的 scale | `sub_1424ED580` 里 `100000LL * (int)v + (小数 × 3276800000 >> 15 >> 15)`，`3276800000 = 100000 × 32768` |

`sub_1424ED580` 的关键几行：

```c
n922337201 = *a2 >> 15;                     // 输入是 CFixedPoint64
if ( (int)n922337201 <= 922337201LL )       // (int) 就是 32 位截断
  if ( (int)n922337201 >= -922337201LL )
    *a1 = 100000LL * (int)n922337201 + ...; // 输出是 CFixedPoint
```

## 能不能改成 64 位

**理论上：可以，前提是把变量系统的值类型从 `CFixedPoint` 换成 `CFixedPoint64`。**

**实际上：等于重构引擎，不可行。**

改动会同时牵连：

1. **类型大小**：4 → 8 字节
2. **所有持有该类型的结构体布局**：字段偏移全部作废
3. **千级访问点**：经济、人力、AI 评分、修正值、触发器都读变量
4. **44 个变量系统类**：值类型是模板参数，必须跟着换
5. **存档格式**：字节数变了，新旧存档互不兼容
6. **存档校验**：跟着改

**「只让某些运算走 64 位、存储保持 32 位」这类局部方案也无效** —— 结果最终仍要写回
32 位存储，超过 `2^31-1` 照样丢。

**最强的旁证**：官方 2026-05 的选择是在 32 位里重新分配位宽（21M → 2.1B），
不是升 64 位。**如果升 64 位容易，他们早就升了。**

## 真正可行的替代：双变量模拟 64 位

完全不碰游戏代码的做法 —— 用两个 32 位变量表示一个 64 位量：

    x_hi  高位（单位 10^9 或 2^31 的倍数）
    x_lo  低位

所有加减在脚本里手工进位。

| | |
|---|---|
| 优点 | 不碰游戏、存档安全、可分发 |
| 缺点 | 所有运算要自己写，不能直接用 `multiply_variable` |

**这是唯一真正可行的方案。**
