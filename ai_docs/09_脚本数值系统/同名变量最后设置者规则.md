# 同名变量的最后设置者规则

2026-10-12。规则作用于原版解析后同一个容器里的同一个变量，不是全局只按名字分类。

## 当前合约

| 最后执行的有效设置 | 结果 |
|---|---|
| set_variable64 | 使用 persistent variable64 三槽表示；重建完整整数/小数值，撤销该变量的旧挂账 |
| set_variable | 使用原版表示；撤销既有三槽身份并清理该变量的旧挂账 |

set_variable64→set_variable、set_variable→set_variable64，以及同一种 setter 重复设置均支持。
这里的“原版表示”不是浮点类型的承诺；不把 set_variable 的所有内部数值布局笼统称为 32-bit float。
原版 add_to_variable 等已接入算术在本轮输入中继续遵循当前身份，不因为变量曾经用过 _64 就永久按 _64 处理。
同名但容器不同的变量相互独立；temp 遮蔽是读取优先级，不能与重设持久化变量的精度归属混为一谈。

## 原已有行为与本轮缺陷

Var64_GameSyntaxDetour 原先在原版 setter 执行前记录 was64，执行后调用 Var64_ClearHighPartAfterVanillaSet。
该清理将 _var64h/_var64f 置零并移除进程内名称记录；辅助槽可以仍存在，但 frac 身份标记失效。
Var64_DoSetVariable64 重写三槽，因此正常的最后 setter 归属原先已经成立。

本轮在国家、另一国家、州、角色、global 做普通切换、负数、后续加法与 320 次交替写入：45/45 正常检查通过。
但此前的进程内溢出挂账没有随 set 清理。基线的两个额外用例都错误回到 2147483647.99999：

1. 原版变量与大数 variable64 操作数运算形成挂账，set_variable=2.5 后加 0.25，应为 2.75。
2. 形成挂账后 set_variable64 建立新值，再 set_variable=3.5 后加 0.25，应为 3.75。

新增 Var64_ResetDebtForSet，通过容器+名字调用 Var64_FindDebt/Var64_ClearDebt。
set_variable64 完成解析与写入后清理旧债；原版 setter 处理完成后也清理目标旧债，不要求 was64 为真。
仅匹配目标容器与名称，不清理另一容器同名记录。辅助身份撤销逻辑仍保留，未改全局命名方式。

## 验证结果

| 验证 | 观察 |
|---|---|
| 游戏基线 | 45/47，只有两个挂账重新赋值边界失败 |
| 修复后即时游戏检查 | 47/47，包含实际三槽身份/辅助值的只读采样，不只看显示 |
| 重启读档 | 五种容器的原版/64 位最终值各一，共 10/10；marker=20261012 |
| 合计 | 57/57，相关事件解析错误 0，游戏存活 |
| 原生真实 setter 函数夹具 | 9/9；基线 5/9，独立源副本回滚 5/9，stdout/退出码逐字相同 |

原生夹具 mock 原版变量写入/容器依赖，编译实际 Var64_DoSetVariable64、Var64_GameSyntaxDetour 与挂账读取。
包含另一 scope 同名挂账不受影响、无法解析的 set_variable64 不改旧状态；不把此项推广为所有非法原版 setter 的行为。
本轮保存 swmode：命令 ok=1、验证新文件，再退出并 -continuelastsave 重启；不以旧存档或进程退出码代替保存成功。
重启后的原版值为 -1.5、64 位值为 12345678901.125；已检查身份，而非只比较本地化文本。

最初只读探针错误按环形表回绕，导致州/角色/global 有 3 个身份假阴性；已按生产 lookup 的连续 spill 路径修正。
原始 baseline 探针记录保留；baseline_verified 才是正确只读探针的基线结果。

## 复现入口与证据

verify_setter_ownership.py PHASE --deploy --lifecycle：先完成 Release x64 构建，PHASE 使用新名字。
--attach 只用于已加载同一 fixture 的进程；--verify-only 重查已有捕获。
test_setter_debt_native.py SOURCE OUTPUT：同输入编译源文件，检查有效值、身份、挂账与容器隔离。

Evidence：test/reports/20261012_variable64_transaction/setter 的事件、expected、日志、只读 samples、存档与原生输出。
Finding：正常三槽身份切换已存在，但进程内挂账使重新赋值语义不完整。
Path：确认普通切换绿灯与挂账红灯，最小清理补丁，再完成即时/重启/原生回滚与相关回归。
四角色继续沿用该事务根目录，补丁和 rollback 不操作正式战役存档。

## 边界

本轮仅验收所列有效 setter 序列；非法输入、分配失败、动态同名冲突、数组/所有前缀链、
专用 add_to_variable64 与挂账混用、热读档、多线程与多人仍需要专项验证。
挂账本身仍为进程内状态，不因本轮普通三槽存档成功就宣称挂账已持久化。
