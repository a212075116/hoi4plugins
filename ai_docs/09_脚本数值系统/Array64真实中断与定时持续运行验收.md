本轮沿用正式DLL，不新增effect/trigger，也不改变生产源码。测试对象是此前配对完毕的prf与单人测试存档。
DLL SHA256：72704dfaa4cc5485425841a19a34f38a866bc88c9f72a7743b1dcc7ca9b41070。
中断/恢复/持续操作/重载功能断言137/137通过，fixture解析错误0，检查退出0，最后游戏存活；资源增长尚待归因，不视为资源发布验收完成。
这里的真实中断是对游戏进程执行taskkill /F /PID；不是修改保留字段模拟故障，也不是掉电测试。

## 中断点与实际证明

公开事件执行append_array64。Frida只设置确定性的暂停门，不替换后端、不注入任意返回值、不改原生数组字段。
在门处记录原生表状态、意图文件字节和进程PID，再由宿主终止该PID。
使用事先打开的Windows进程句柄，WaitForSingleObject返回0且GetExitCodeProcess不是STILL_ACTIVE，才承认终止完成；不依赖tasklist的一次即时输出。
三份完成验收的记录均保留taskkill stdout/stderr/退出码、OS等待结果、进程退出码、未完成的原生事件命令及重启结果。

| 中断门 | 门处观察 | 重启旧检查点 |
|---|---|---|
| WriteFile已返回，临时文件尚未刷新/替换 | 正式侧车哈希不变；generation=6，无receipt；临时文件残留 | 五scope恢复status=0，值与长度正确 |
| 新意图已经替换并重开核对，首次receipt写入之前 | 正式侧车哈希改变；generation=6，无receipt | 国家恢复返回-5，其他scope为0；旧值不被覆盖 |
| 部分元素已真正写入，hi^1尚未写入 | generation=7，receipt phase=1，新增lo^1=-100000；manifest长度仍1 | 加载旧存档而不是瞬时内存；国家恢复返回-5，旧值/长度正确 |

后两例恢复原检查点的精确配对侧车，再调用公开recover，五scope均为0、值12345678901.125、长度1。
真实内存的部分写入没有被假装成已保存状态；本轮重载的是操作前检查点，不是中断瞬间自动保存。
实际游戏内存的奇数generation/部分receipt恢复已在之前的“故障状态保存重启”用例验证；不要混为一次真实强杀中的原子存档证明。

## 临时文件残留

临时文件写入后终止会留下prf.a64j.<PID>.<nonce>.tmp。下一轮操作使用新的PID/nonce，正式侧车不读取该残留。
本轮在保留该残留期间继续了另两个中断测试和持续操作，再逐字节归档、核对哈希、删除本轮精确匹配路径。
早期测试宿主中止留下的两个已知临时文件也逐份归档清理，没有递归删除目录或清理其他人的文件。
生产插件当前没有启动时自动清理孤儿.tmp的功能；反复中断可能积累残留，这属于运维注意事项，不声称已经自动解决。
清理前停止游戏并保留证据；只处理确认属于已终止操作的临时文件，不能删正式.a64j来“修复”。

## 定时持续操作

五scope均参与；每批每scope4轮append→insert→set_native→set64→erase首项→erase尾项，每批120次effect。
每批核对完整精度与长度1，持续至少180秒；批次之间留0.5秒给游戏其他执行流，不把180秒空等算为压力。
只统计本阶段新增插件日志；所有操作必须status=0，五scope每批检查都必须通过，缺日志也失败。
定时记录工作集、PrivateUsage与句柄数，保存后退出重启，再核对全部值/长度和恢复结果。
180秒属于有界持续事件压力，不是多小时soak，也不证明内存泄漏已排除。
测试主要通过控制台事件驱动；日志中的游戏日期仍为500.1.1，不将墙钟持续时间当作多年战役推进。

本次55批、6600次effect，墙钟181.98秒；全部6600项status=0，275项批次值/长度检查通过，存档重启也通过。
工作集增加290037760字节（约276.60MiB）、PrivateUsage增加297238528字节（约283.47MiB）、句柄增加38。
随后重启后的同长度180秒无控制台RPC空闲观察：工作集减少5636096字节（约5.38MiB），PrivateUsage减少3227648字节（约3.08MiB），句柄增加31。
该空闲观察的启动预热时点不严格相同，没有空事件/原版数组对照，不能据此直接归因插件或断言泄漏。
但压力期私有内存增长不应被忽略；下一步先比较等调用数空事件、原版平衡数组操作和Array64，再延长运行。句柄在空闲期也增长，不能把全部句柄变化归咎Array64。

## 复现与配对备份

在与此前lifecycle_v1一致的测试环境运行；先保存自己的进度，本脚本会多次结束游戏进程。
已有phase拒绝覆盖；基线需为五scope健康prf、长度1、值12345678901.125、国家generation=6，且侧车配对。

```powershell
python -u test/modules/effect/verify_array64_api_crash_soak.py new_phase --seconds 180
python test/modules/effect/verify_array64_api_crash_soak.py new_phase --verify-only
```

保存检查点a64kill用于三次中断重启，持续运行结束保存a64soak；同时归档五scope最新侧车及其哈希。
持续操作会推进generation、替换最新意图，因此测试结束后不要拿旧recovery_v3/lifecycle_v1侧车强行匹配新的a64soak。
继续测试必须使用本轮新的配对存档及侧车；旧报告仍保留为历史证据，而不是当前可执行状态。
只延长持续操作时可用--soak-only，不再重跑已完成的三种中断门；首次完整中断矩阵仍有generation=6的前提。
本轮尚未跑长时版本，资源对照归因前不建议直接延长到多小时。

## 宿主修正与剩余限制

首轮保存Frida借用retval对象导致后续回调复用该对象，读到0x19错误；改为复制指针值，保留失败记录，并恢复原测试侧车。
后两轮宿主用即时tasklist/RPC线程结束判断死亡，断言失败；改为精确进程句柄等待与退出码证据，不把这些未完成矩阵的尝试当通过。
如果Frida同步RPC未及时结束，仅在OS死亡确认后完成宿主destroy通知；该宿主异常不当作原生应用崩溃诊断。
最终矩阵是独立的新phase，早期输出没有覆盖；未修改生产实现去迎合测试门。
没有验证真实掉电、硬件缓存持久性、任意时间崩溃、游戏存档与侧车联合原子性、多小时soak、多人与GUI视觉。
