公开恢复/异常/中断/压力/重启核对330/330断言通过，fixture解析错误0，最后游戏仍存活，测试退出0。

## 本轮修复：首次使用空变量容器

此前五 scope 的接口用例先创建了普通标量/原版数组，掩盖了空容器路径。
新的角色用例先执行 create_array64，发现首次创建 status=-2，后续 set/append 因身份不存在返回-902；之后创建另一个组反而成功。
实际原生 resolver 返回了相同角色容器，第一次表头为非空静态哨兵指针、mask=0、count=0、spill=0；状态槽写入后才分配普通变量表。
因此不是角色 scope 不支持，也不是已有专属字段碰撞，而是只读后端把合法空表误判为损坏。

修改 native_array_readonly.c 的 na_lookup 和 array64_group_readonly.c 的 ag_inventory，统一使用 na_empty_table。
仅 mask=0 且 count=0、spill=0、哨兵可读且未占用时判定为不存在/零项；异常 spill、计数、已占用哨兵、空指针仍拒绝。
这只是只读判定，不向空容器补造数组；实际创建仍通过原版 upsert 分配。
variable64.c 保持原哈希，旧 indexed64 拒绝逻辑未改。

同输入 MSVC 夹具：BASELINE 2089/2091、exit=1；MODIFIED 2091/2091、exit=0；ROLLBACK 2089/2091、exit=1。
两项原始失败均为空表“不存在”语义；回滚副本的两个源码哈希与修复前相等。
原生日志后端夹具244/244；旧注册/tooltip/索引边界夹具22/22、16/16、8/8再跑通过。

## 持久化中断状态与压力设计

通过原版 set_variable 设置匹配的 nonce/receipt、奇数 generation，并扰动元素低位，构造中断状态。
这是测试夹具的显式故障注入，正常模组不得改保留字段；不是实际强杀进程的崩溃测试。
故障状态先保存并重启，再由 recover_array64 从匹配的正式侧车恢复 append 前基线。
查询奇数 generation 时返回 false，不把隔离值当零；恢复后再次恢复应幂等，随后再保存并重启核对。

每scope连续32循环：append→insert→set_native→set64→erase；五scope共800次循环内操作。
另有5次创建和5次resize到256，共810次 pressure 组公开操作，逐条核对插件状态。
核对长度、保留元素完整精度与新增尾部零；存档重启再核对各scope首项、尾项、长度。
单独创建4096元素组，验证第4097次追加、索引4096写入和长度4097被拒绝，长度仍为4096。
有界压力不等于数小时 soak、帧率性能基准或内存泄漏证明。
本次所有810次pressure组操作status=0；压力事件加保存整体约11.12秒，仅供本机复现参考，不当作通用性能指标。
五scope的中断状态存档重启后恢复为 [12345678901.125]，重复恢复状态0；再次存读档仍保持该值及长度1。
压力组存读档后长度256、首项12345678901.125、尾项0，4096边界组长度仍4096。

## 复现与证据

在项目根执行：

```powershell
python -u test/modules/effect/verify_array64_api_recovery.py new_phase
python test/modules/effect/verify_array64_api_recovery.py new_phase --verify-only
```

脚本部署 build/Release DLL，重启游戏，使用测试模组 bakaifa，保存 apr64；已有 phase 拒绝覆盖。
仅在该单人测试环境运行，运行前保存自己的游戏进度；自动化会结束当前游戏进程。
Evidence：test/reports/20261012_variable64_transaction/api/recovery_v3 的 commands、日志、侧车快照、存档及 comparison.json。
Finding：空角色首次创建缺陷已修正；正常恢复与25例异常文件拒绝保持当前数组不变。
Path：精确空表判定回归→正式构建→公开恢复/持久化故障/压力→交付包重建与副本回滚。

第一次游戏测试和第二次误部署旧DLL的失败记录保留。项目单独构建必须指定 SolutionDir；本次已校对实际部署 DLL 哈希。
