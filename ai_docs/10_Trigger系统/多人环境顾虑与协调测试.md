# 多人环境顾虑与协调测试

2026-10-12。当前开发与验收以单人为主；已有单人结果不构成联机同步保证。
本页是日后协调测试的风险清单，不是已确认的多人故障报告。

## 需要顾虑的事项

| 对象 | 风险与需要验证的点 |
|---|---|
| 插件、游戏、mod 版本 | 所有参与者应使用同一游戏版本、同一插件 DLL 和同一脚本/本地化文件；比较 SHA-256，不能只看文件名。RVA 与虚表布局为版本绑定，错误版本应拒绝注册而非继续运行。 |
| 注册与测试开关 | token 与注册次序可能影响脚本解析；各端成功注册名称、数量和初始化结果必须一致。不得一端启用 HOI4_TRIGGER_REG_STRESS、另一端关闭。热注册/卸载不在当前支持范围。 |
| Trigger 求值 | 条件可能在各端重复求值；回调必须只读、无副作用。不读取系统时间、随机宿主值、鼠标/摄像机状态、本地文件或仅一端存在的缓存来决定同步游戏条件。 |
| variable64 三槽 | 主槽、_var64h、_var64f 需要作为同一逻辑值观察；确认所有端的作用域容器、读写顺序、raw 值和脚本结果一致，不仅比较格式化文本。 |
| 进程内挂账 | 目前挂账是进程内状态，不能据三槽存档成功推断挂账已持久化或会同步。重连、热加入、存档重启可能使各端缓存不同；相关场景在测试前不要视为可靠。 |
| 摄像机 Effect | 摄像机通常是客户端本地呈现。Any scope 只是允许调用，并未证明原版网络会广播或隔离这些修改。检查是否只影响预期客户端，不要把摄像机值用作同步规则输入。 |
| 日期 Effect | 日期属于全局游戏状态。需要确认指令在主机/客户端的实际执行路径、次数与权限；重复执行可能导致日期偏移。未验证前不建议在联机脚本中使用。 |
| 原生对象生命周期 | 读档、热加入、断线重连可能替换上下文或变量容器。不得缓存槽地址跨生命周期；检查过期地址、身份与容器隔离。 |
| 性能与线程 | 单人算术/条件测试不代表多人调度安全；不支持任意线程注册。观察大量条件求值是否造成卡顿、超时或日志放大。 |

## 协调测试的最小安排

准备两台独立机器，一人主机、一人客户端；使用独立测试存档，不覆盖正式战役。
先关闭所有可选抗压注册开关，用基础配置建立联机基线，再逐项打开测试。
记录游戏版本、mod 列表、插件/事件文件 SHA-256、启动参数、注册摘要和各端本地时间。
时钟仅用于对齐记录，不作为游戏条件输入。

按以下顺序推进，每一阶段先通过，再扩大测试人数与事件频率：

1. 无插件基线与同配置插件启动；核对原版 checksum、注册结果与脚本解析错误。
2. Bool 与数值/块 Trigger 的真/假、NOT/AND/OR；在相同游戏时刻收集各端结果。
3. 同名变量在国家/州/角色/global 容器内隔离；ROOT/PREV/FROM 操作数与三槽 raw 对比。
4. 主机触发一次、客户端触发一次、同 tick 多次触发；确认权限与实际执行次数，没有重放或漏执行。
5. 保存并重启、客户端重连、热加入、主机交换；分别验证普通三槽与挂账状态，不合并结论。
6. 最后测试日期、摄像机和逐步升高的算术/条件负载；日期类使用可丢弃存档。

## 每轮需要保存的证据

各端 game.log/error.log/插件日志、事件脚本原文、输入值、所属 scope、三槽 raw 值、
条件结果、日期、命令返回、触发次数、存档 SHA-256，以及 OOS 提示/诊断文件（若游戏生成）。
用游戏日期/事件标记关联记录，不以两台机器的墙钟顺序推断游戏执行顺序。

判断门槛：各端对应输入与结果一致，无本轮脚本错误、崩溃、重复状态修改及 OOS；
重复运行后结论仍一致。任何差异先保留双方记录，缩减成单事件复现，不通过重载旧存档掩盖。
发生异常时退出该测试轮、恢复各端相同已验证版本，确认文件哈希后重新建立基线。

## 当前结论

多人实测尚未完成；本页所有风险项保持待验证。单人优先不等于忽略联机风险：
实现阶段保持 Trigger 只读、变量原版容器解析和明确版本检查，给后续协调测试留出证据入口。
