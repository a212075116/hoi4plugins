## 五、64 位兼容 32 位运算的设计草案 (用户方案, **一行代码都还没写**)

### 5.1 存储 (保持现状, 不改)

```
x    槽 = lo(低 32 位, int32 补码) x 100000
x_hi 槽 = hi(高 32 位, int32 补码) x 100000
x_f  槽 = (frac + 100000) x 100000
```

### 5.2 运算时的十进制分段 (用户称之为"临时缓存")

```
整数部分 V_int = H x 10^9 + L9      H <= 92233, L9 in [0, 999999999]
小数部分 F     in [0, 99999]
```

选 9 位而不是 10 位的原因: 低位段要参与运算, 加一次就可能超过 2^31;
L9 <= 999999999 时, 999999999 + 999999999 < 2^31, 留出裕量。

### 5.3 段内运算规则 (用户口述, 未实现)

```
加法: F += bF; 若 F >= 100000 则 L9 += 1, F -= 100000
      L9 += bL; 若 L9 >= 10^9 则 H += 1, L9 -= 10^9
减法: F -= bF; 若 F < 0 则 L9 -= 1, F += 100000
      L9 -= bL; 若 L9 < 0 则 H -= 1, L9 += 999999999
乘法/除法: 用 128 位中间量再落回分段 (避免 9.2e18 x 2e9 这类必然溢出)
```

### 5.4 溢出挂账机制 (用户已确认理解一致, 未实现)

```
当 32 位值要跌破 -2147483648 (或它与 64 位做减法的结果要跌破) 时:
  1) 32 位值锁死在 -2147483648
  2) 把 64 位值拆成 高位/低位/小数 三个分量挂账暂存, 64 位值自身清零
  3) 之后凡是对这个 32 位值做加法, 都先检查它是否挂着未完成的 64 位运算
  4) 挂着就先拿这次加法去抵消三个分量; 三个分量不归零之前, 不允许对该 32 位值做任何运算
```

### 5.5 三类运算的分派 (用户口述)

| 情况 | 用谁的算法 |
|------|-----------|
| 两个都是 32 位 | 原版直接算 (我们完全不介入) |
| 两个都是 64 位 | 我们的算法 |
| 一个 32 位一个 64 位 | 让 64 位的低位与 32 位算, 低位到 0 向高位借位并回填 999999999 |

// 小数先归整

# 附二: 三个 64 位运算 effect 已实现并验证 (2026-10-11 16:43:41)

## 已落地的 effect

| effect 名 | 语义 | 语法 |
|-----------|------|------|
| modulo_variable64 | 取余 (与原版同: 先舍小数再整数取模) | `modulo_variable64 = { var = x value = 1000 }` |
| round_variable64 | 四舍五入 (与原版同: 恰好 .5 时取绝对值大的方向) | `round_variable64 = { var = x }` |
| clamp_variable64 | 低于下限时提升到下限 | `clamp_variable64 = { var = x value = <min> }` |
| clamp_variable64_max | 高于上限时压低到上限 | `clamp_variable64_max = { var = x value = <max> }` |

## 为什么 clamp 拆成两个 effect (重要限制, 已实测)

原版 clamp_variable 的参数是 `var` + `min` + `max`, 位于实例偏移 +88 / +296 / +504。
但我们的自定义 effect 是通过借用 set_variable 的 entryVt (RVA 0x277C418) 来获得参数解析的,
而**该 entry 只认识 var 与 value 两个参数名**, 额外参数名 (min/max) 根本解析不进来。
实测: `clamp_variable64 = { var = x min = 0 max = 1000 }` 直接导致 effect 执行报错 (out->ok = 0)。
因此改为用 value 传边界, 并拆成下限/上限两个 effect。
**若要支持原版一模一样的 min/max 语法, 必须拿到 clamp_variable 自己的 entryVt, 这仍待解决。**

## 已知的两个坑 (都是实测踩出来的)

1. **测试值不要超过 92233720368547.75807**(游戏定点 raw 的 int64 上限)。

# 附三: clamp_variable 的 min/max 机制 (逆向结论 + 未解决卡点) 2026-10-11 17:00:59

## 一、原版 min/max 的确切机制 (静态反编译, 可信)

从 clamp_variable 的执行体 sub_14034F750 读出:

```c
var: a1 + 88           变量槽 (sub_140542280(a1+88, ctx, 0))
min: a1 + 296          存在标志在 a1 + 304
max: a1 + 504          存在标志在 a1 + 512
读值: sub_140544C90(a1 + 296, &minVal, ctx, 0, 0);
      sub_140544C90(a1 + 504, &maxVal, ctx, 0, 0);
```

语义来自游戏内 effect 描述字符串(从 effect map 里读出的原文):

> Clamps a variable between two values or variables.
> Note that either min or max can be omitted.
> The order in which the operations are applied is **Max( Min( var, max ), min )**.
> An error will be logged if max < min ...

即: 先与 max 取小, 再与 min 取大; 两者都可省略。

## 二、effect entry 的结构 (从 effect map 遍历得到)

effect 注册表就是一棵 std::map<int, Entry*> 红黑树 (断言字符串:
"_EffectEntries.find( Token ) == _EffectEntries.end()", effect.cpp:83),
节点 +32 是 token id, +40 是 entry 指针, entry+8 是描述字符串。实测共 569 个 effect。

每个 effect 的 entryVt 数组是 0x18 一组, 三个指针:

```
+0x00  通用 vtable       (实测各 effect 都是 0x1402E2FF0)
+0x08  factory 函数
+0x10  数据指针 (参数相关)
```

clamp_variable 的这组在 RVA 0x277C680, clamp_temp_variable 在 0x277C638,
set_variable 在 0x277C418, 游戏默认模板 STAB_ENTRY_VT 在 0x277CED8。

## 三、未解决的卡点 (实测证明)

目标: 让自定义 effect `clamp_variable64 = { var = x min = 0 max = 1000 }` 能用原版语法。

已试过但**无效**的三种做法:

1. 把 entryVt[0] 换成 clamp_variable 的 vtable  -> 无效
   (实测各 effect 的 entryVt[0] 本来就是同一个 0x1402E2FF0)
2. 额外拷贝 entryVt[2] = clamp 的 +0x10 数据指针 -> 无效
3. 直接转发给原版 clamp 的执行体 sub_14034F750 -> 无效
   (effect 报 ok, 但 min/max 没进实例, clamp 静默不生效)

实测现象: 用 clamp 的 entryVt 创建实例后, 从 +200 读变量名读到的是字符串 "max",
说明 clamp 的实例布局里 +200 不是变量名, 与 set_variable 的布局不同。

结论: **参数名 -> 实例槽位的映射不在 entryVt 里**, 应该在 effect 的"参数注册"环节,
这一层尚未挖到。

## 四、当前可用方案 (已验证)

用 value 传边界, 拆成两个 effect:

```
clamp_variable64     = { var = x value = <min> }   低于下限则提升
clamp_variable64_max = { var = x value = <max> }   高于上限则压低
```

实测:

```
M64 t5=1000    clamp_variable64 345 -> 1000
M64 t6=100     clamp_variable64_max 1000 -> 100
M64 t4=1000     clamp_variable64_max 9999999999999.99999 -> 1000
M64 t8=-1000   clamp_variable64 -5000 -> -1000
```

注意: 写成 `{ var = x min = 0 max = 1000 }` 时 min/max 会被**静默忽略**(不报错也不生效),
所以文档必须明确写出用 value 传边界。

# 附四: 四个算术运算符已接入 64 位 (2026-10-11 17:24:48)

## 实现方式

对四个执行体装 InlineHook, detour 里:

```
1) 读实例 +505 的 marker -> 命中我们的 effect 分支则走现有逻辑
2) 否则只读 +200 的变量名, 查 64 位登记表 (廉价过滤, 零副作用)
     不在表里 -> 立刻转原版执行体
     在表里   -> 走 64 位运算, 原版执行体不执行
3) 原函数指针为空时返回 0
```

RVA (静态反编译 + 运行期探针双重确认):

```
add_to_variable        0x14034C760
subtract_from_variable 0x140366BC0
multiply_variable      0x14035B9E0
divide_variable        0x140355C70
```

## 64 位运算的定点换算 (关键)

```
当前值 raw = vInt x 100000 + vFrac      (从三分量读出)
操作数 raw = 参数值 (引擎已给定点 raw)

加减: 分别对整数/小数段运算后归一化 (小数满 100000 进 1, 不足则借位)
乘法: rawProduct = (rawA x rawB) / 100000   -> 再拆成整数/小数
除法: rawQuot    = (rawA x 100000) / rawB   -> 再拆成整数/小数
      除数为 0 时保持原值并记日志
      128 位中间量 (MSVC _umul128) 避免溢出
```

## 实测 (全部通过)

```
add:      100 + 5 = 105;  105 + 0.25 = 105.25;  92233720368546.05 + 1 = 92233720368547.05
subtract: 100.5 - 0.5 = 100;  1000000.5 - 1000001 = -0.5
multiply: 100 x 3 = 300;  12.5 x 0.5 = 6.25
divide:   300 / 4 = 75;  7 / 2 = 3.5;  除零 -> 原值不变
32 位变量: 全程走原版路径, 插件日志里没有任何记录
```

## 两个致命坑 (已修正, 记录以防重犯)

1. **不能在 effect 的 hook 里调用本地化上下文的函数**
   Var64_LangResolveSlotValue 要求 ctx 是本地化上下文, 在 effect 作用域里调用会直接崩溃
   (实测崩溃目录 crashes/hoi4_20261011_171531, 发生在进图 Resetting game 之后)。
   替代: 用实例自身的 Var64_ResolveAddressByName。
   另外热点路径上必须先做廉价过滤(只读名字查表), 否则游戏内部的频繁调用会出问题。

2. **乘除的定点缩放不能少**
   `lo / 100000` 是定点 raw 而不是整数部分; 直接当整数部分会导致结果放大 10 万倍
   (100 x 3 得到 30000000)。必须再除一次 100000 取整、取余。

# 附五: 操作数参数描述的结构 (关键发现, 2026-10-11 18:40:55)

## 结构 (effect 实例 +296 处, 即 value 参数描述)

```
+0x00  指针 (vtable)
+0x08  标志位; 字节 +0x09 = 1 -> 常量; = 0 -> 变量/表达式
+0x40  常量值 (定点 raw, 例如字面量 7 时 = 700000)
+0x70  变量名 (std::string SSO 缓冲)
+0x80  size (名字字节数)
+0x88  capacity (15 = SSO 内联)
```

## 实测对照

```
字面量 7:      +08 = 0x0101      +70 = 0
64位变量 ry:   +08 = 0x0001      +70 = 0x7972   -> 'r','y'
32位变量 rz:   +08 = 0x0001      +70 = 0x7A72   -> 'r','z'
```

## 为什么必须自己读这个名字

我们的存储把小数放在独立分量 _f 中, 而游戏的参数求值器只读主槽,
因此 `multiply_variable = { var = px value = pz }` 里 pz = 2.5 只会给出 2。
自己拿到名字后按三分量读, 才能得到完整的 2.5。

## 修复后的实测

```

VN v4=276.25    2762.5 / 10
PD b=109.5      107 + 2.5
PD c=113        109.5 + 3.5
```

## 注意

目前只处理了 +296 (value / min 位置) 的参数描述。
如果将来要支持 value 指向作用域变量 (如 ENG.xxx) 或 clamp 的 max(+504),
需要按同样规则读对应偏移的参数描述。

# 附六: 溢出挂账机制 (加减法) 实现状态与已知缺陷

## 数据结构

```c
typedef struct {
    char      name[40];
    long long debtInt;
    long long debtFrac;
    int       active;
} Var64DebtRecord;
static Var64DebtRecord g_var64Debts[64];
```

## 状态机

```
挂账不存在 + 结果超 int32 -> 变量锁定边界值, debt = 真实结果 - 锁定值
挂账存在 -> 任何加减只抵扣 debt, 变量值不动; debt >= 0 时结算
结算 -> 变量 = 边界值 + 剩余 debt, 清除挂账, 恢复正常
```

## 已知缺陷 (未修复, 需要继续定位)

1. **结算数值偏差 3100**
   100 - 5000000000 + 1000 + 2000 + 2500000000 + 1000000000 应为 -1500000000,
   实测 -1499996900, 偏差 3100 (= 1000+2000+100)。
   怀疑: 首轮建立挂账时把当前值也计入了债务, 或结算路径重复累加。

2. **显示双负号 --2147483648**
   32 位变量锁死期间, [?dy] 显示为 --2147483648。
   怀疑: 桥接格式化或槽值换算问题。

## 乘除法挂账的可行性 (结论: 可以, 但语义需确认)

挂账本质与运算类型无关, 乘除法同样可算完整结果后记账。
**但加减法挂账是线性可抵扣的, 乘法挂账不是** ——
乘法溢出的债务无法通过简单加法线性抵消, 所以乘法挂账应当:
只锁定 + 记录, 期间拒绝任何后续运算并记日志, 直到显式 set_variable 重置。
此点待用户确认。

# 附七: 溢出挂账机制 (加减法) 完成 (2026-10-11 18:59:44)

## 最终规则

```
挂账不存在 + 结果超 int32 -> 变量锁【可显示的极值】, 差额全额计入挂账
挂账存在 -> 任何加减只抵扣挂账, 变量值不动 (字面量与变量操作数都支持)
挂账 >= 0 -> 结算: 变量 = 锁定值 + 剩余挂账 (用 raw 直接相加, 精确)
```

## 两个必须记住的技术点

1. **锁定值不能用精确的 int32 边界**
   -2147483648 会让游戏自己的定点格式化出错(显示成 --2147483648),
   因为它在算 |raw|/100000 = 2147483648 时超出 int32 正范围。
   改用 -2147483647.99999 (raw = -214748364799999) 显示正常,
   差的那 0.00001 计入挂账, 数学仍然精确。
   正方向同理用 2147483647.99999。

2. **挂账变量的判断不能只看 64 位登记表**
   `if (debt == NULL && IsSixtyFourBitName(name)) return 0;`
   即: 只要这个变量身上有挂账, 无论它是否登记过, 都必须走抵扣路径。

## 实测(精确性验证)

```
create: locked=-214748364799999 debtInt=-2852516253 debtFrac=99999
settle: baseRaw=-214748364799999 debt=647486747/99999
        newRaw=-149999690000000   -> -1499996900  精确
```

## 乘除法挂账的结论

可以同构, 但加减法挂账线性可抵扣而乘法不是, 所以乘法挂账应只锁定 + 记日志,
期间拒绝后续运算, 等显式 set_variable 重置。待用户确认。
