## 一、尚未解决的问题

### 1.1 clamp_variable64 的原版 min/max 语法 (卡住)

目标: 让 `clamp_variable64 = { var = x min = 0 max = 1000 }` 能用原版语法。

原版 min/max 的位置已经查清 (静态反编译, 可信):

```c
var: a1 + 88           变量槽
min: a1 + 296          存在标志在 a1 + 304
max: a1 + 504          存在标志在 a1 + 512
```

语义来自游戏内 effect 描述字符串 (从 effect map 遍历读出):

> Clamps a variable between two values or variables. Note that either min or max can be omitted.
> The order in which the operations are applied is **Max( Min( var, max ), min )**.

**已试过但无效的三种做法**:

1. 把 entryVt[0] 换成 clamp_variable 的 vtable -> 无效 (实测各 effect 的 entryVt[0] 本来就是同一个 0x1402E2FF0)
2. 额外拷贝 entryVt[2] = clamp 的 +0x10 数据指针 -> 无效
3. 直接转发给原版 clamp 的执行体 sub_14034F750 -> 无效 (effect 报 ok, 但 min/max 没进实例)

实测线索: 用 clamp 的 entryVt 创建实例后, 从 +200 读变量名读到的是字符串 "max",
说明 clamp 的实例布局里 +200 不是变量名, 与 set_variable 不同。

**结论: 参数名 -> 实例槽位的映射不在 entryVt 里**, 应该在 effect 的"参数注册"环节, 尚未挖到。

### 1.2 modulo / round / clamp 三个原版 effect 未接入

目前这三个是独立的 `_64` 后缀 effect (见 `变量运算effect的64位版.md`),
没有像加减乘除那样 hook 原版同名 effect。原因: modulo 的实例布局是 +32/+240,
与其余运算符的 +88/+296 不同, hook 不能套用同一套偏移。

## 二、待用户确认的设计问题

### 2.1 乘除法挂账的抵扣语义

加减法挂账是**线性可抵扣**的 (y += 5 债务就减 5)。
但乘法挂账**不是线性的**: `y x 1000` 溢出后, `y += 5` 无法线性抵消债务
(债务是"y 还得再乘几次才补得上"的关系)。

用户 2026-10-11 提出的统一方案 (尚未打通):

> 把三个分量和溢出后的 32 位值合并成一个真 64 位数 (在 C++ 内部算好),
> 用这个真 64 位数做乘除运算; 算完判断是否大于 32 位最大值:
> 大于就把溢出数还给 32 位值, 接着把真 64 位数拆成三分量;
> 否则直接把真 64 位数设给 32 位值。乘法数值小于 1 时同理。
> 如果真 64 位数也要溢出了, 则一律默认 2^63-1, 尽量防止溢出。

**实现状态**: 骨架已写 (`Var64_ReadTrueRaw` / `Var64_WriteTrueRaw`),
但乘法路径尚未打通 —— 实测 `MB a2=605618481.25806` 说明乘法没进我们的分支
(插件日志里完全没有乘法记录), 待加日志定位入口。

### 3.3 参数读取器的最后一个参数 (语义仍未验证)

```c
// set_variable (sub_140364C60)
sub_140544C90(a1 + 296, &v8, a2, 0LL, 1u);   // 最后一个参数 = 1

// add/subtract/multiply/divide
sub_140544C90(a1 + 296, &v8, a2, 0LL, 0);    // 最后一个参数 = 0
```

实测结论: 这个参数**不影响小数保留** (改过之后 `1105 x 2.5` 依然是 2210)。
小数丢失的真正原因是游戏求值器只读主槽, 与这个参数无关 (见 `变量运算符64位接入.md` 第四节)。
它的确切语义仍未查明。
