# 崩溃排查

> 结论先说：**HOI4 自己就在写崩溃转储，比起源引擎的更全。**
> 不需要我们自己实现 dump 机制。

## 崩溃报告在哪

    Documents/Paradox Interactive/Hearts of Iron IV/crashes/<时间戳>/

每个崩溃一个子目录，里面有：

| 文件 | 内容 |
|---|---|
| **exception.txt** | **异常码 + 地址 + 完整栈回溯（含模块名和源码行号）** |
| **minidump.dmp** | **完整 minidump（实测约 50 MB）** |
| meta.yml | 元信息 |
| logs/ | 崩溃时刻的日志快照 |
| dlc_load.json / mods_registry.json / settings.txt / gameplaysettings.txt | 现场配置 |

**exception.txt 里带模块名 + 行号**，所以多数情况直接看它就够定位，不必开 minidump。

## 工具

    test/lib/crash_report.py

| 用法 | 作用 |
|---|---|
| `crash_report.py` | 列出崩溃总数，显示最新一次完整内容 |
| `crash_report.py -n 3` | 显示最新 3 次完整内容 |
| `crash_report.py --mine` | 只列出栈里含 `hoi4_mod_plugin.dll` 的崩溃 |
| `crash_report.py --copy` | 把最新一次的 exception.txt 复制到游戏根目录 |

## 实例：本项目真实崩溃的定位过程

之前有两次「事件执行后游戏消失、Frida 报 script has been destroyed」，
当时只当是偶发，一直没有定位。

用 `crash_report.py --mine` 一次就查清了：

    Unhandled Exception C0000005 (EXCEPTION_ACCESS_VIOLATION) at 0x00007FF6F624A3B9
    Stack Trace:
      1    hoi4.exe                 PHYSFS_writeULE64 (+ 459161)
      3    hoi4_mod_plugin.dll      Effect_BuildTooltip (effect_reg.c: 132)
      4    hoi4.exe                 PHYSFS_swapULE64 (+ 3434314)

**是我们在 `Effect_BuildTooltip` 里直接写日志（每次 CreateFile/WriteFile/CloseHandle）
造成的。** 已改为「延迟输出」：工具提示里只拷进内存缓冲，下次执行函数再落盘。

## 与 LocalDumps 的关系

系统级 WER 的 LocalDumps 也能配（注册表键：
`SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps\<exe>`，
字段 DumpFolder / DumpType / DumpCount / CustomDumpFlags）。
本机已有 ASUS / NVIDIA / Razer 等条目，**没有 hoi4.exe**。

**对 HOI4 不需要加** —— Paradox 自己的报告已经包含 minidump，且多了栈回溯与日志快照。
若确实想在游戏根目录看到文件，用 `crash_report.py --copy`。

## 排查流程（建议固定成习惯）

1. 游戏异常消失后，**先跑 `crash_report.py --mine`**，不要在日志里瞎找。
2. 看 `exception.txt` 的栈里有没有 `hoi4_mod_plugin.dll`。
   - 有 → 是插件的问题，按行号定位。
   - 没有 → 再看是不是被我们外部杀掉的（taskkill 也会留下一条 tbb_real.DLL 的栈）。
3. 需要更多现场时再开 `minidump.dmp`（IDA / WinDbg）。
